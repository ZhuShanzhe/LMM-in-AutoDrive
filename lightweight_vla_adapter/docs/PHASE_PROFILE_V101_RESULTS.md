# Phase-base 专用图与混合精度对照

## 范围

本记录对应事件模型 `phase_recovery_v1.pt` 的 base 分支，权重 SHA256 为 `5bd639ccb0c09326742c9d5c76a9ddaade7c983d51ce25e0f9d762d64af56fb3`。不包含递归事件头、ModernBERT、观测层、规则层、控制器或新增自行车检测器，不是整链路精度或性能验收。

专用化只在有限值、batch=1、固定输入形状且 `camera_bev` 严格为零时成立；真实 RGB 和 LiDAR 输入保留。输入不满足契约时必须使用完整图，不能把零张量解释为道路空闲。该候选没有替换原生闭环默认 FP32 权重。

224 条归档开发输入中，128 条存在独立标签，另外 96 条缺少标签，未参与准确率计算。逐条输入、标签和模型指纹保存在 `paired_labelled_validation.json`；不是三场景同源 1000 帧验收集。

动作准确率下降 1.5625 个百分点，相对衰减 2.2222%；风险与车道准确率相对衰减均为零。本子集三个分类头的相对衰减均不超过 3%，但绝对精度不能据此称为达到 98%。速度误差增加约 0.0368 km/h，分别呈现，不用分类精度掩盖回归误差。

INT8 只用于投影与 FFN 的选定矩阵乘法；视觉卷积、注意力分数与输出头保持 FP32。量化 BC SHA256 为 `fb80c62d41a19d642fe05ae2f28af4479b42ab4712d0d7adac83823f52a8bf3b`。

SDK 的 x86 BC 功能推理 P95 为 2097.24 ms，ONNX CPU 参考 P95 为 80.34 ms。两种运行器用途不同，不用于计算 BPU 加速率，也不把秒级功能仿真结果当作真实板端性能。

## 同图编译调度

HBDK 4.11.11、目标 `nash-p`、单任务编译。两次使用同一份已校准 BC，仅调整编译调度。

| 编译器预测 | O0、balance=100 | O2、balance=2 |
| --- | ---: | ---: |
| 单图时延 | 约 13.91 ms | 9.1811 ms |
| 每次 DDR 访问 | 370,898,048 B | 108,547,200 B |
| 最小内存需求 | 70,299,600 B | 56,332,880 B |

预测时延降低约 34.0%，DDR 访问降低约 70.73%，最小内存需求降低约 19.87%。优化 HBM 为 30,011,472 B，SHA256 为 `28f2e8fb4c072c9b95f4e109776445a83188a03fcf84fe1e0b51d70e34269f86`。

这些是编译器调度与存储估算，尚无实际 J6P 板卡测量。区间计算单元利用率也不等同于整芯片平均异构利用率，不用于证明评分表的 80% 利用率门槛。BC 功能精度对照与 HBM 调度预测分别保存，不能声称已经完成优化权重的完整闭环验收。

## 原生闭环负载说明

场景二 V101 测试期间，独立采集与离线编译、功能验证均绑定 CPU20；离线任务单线程、低优先级，CARLA 使用 CPU0--19，控制进程使用 CPU21--24。逐帧墙钟计时保留全部样本，包括录屏、采集和并行负载。实际负载说明在 `s2_full_v101_attempt24/actual_background_workload.json`，修正启动器固定文本中“没有编译任务”的不准确表述，原日志不覆盖。

原生场景的任务完成、交通合规和控制提交时延按各场景原始记录判断，不用上述组件预测替代。

## V103 恒定融合分解与 Conv-BN 融合

仅在有限值、固定 batch=1、固定形状且相机 BEV 严格为零的契约下，预计算相机 stem 及其在融合 1×1 卷积中的贡献；保留动态 LiDAR、真实 RGB 和其他输入。融合卷积按输入通道分解，动态分支只计算 LiDAR 贡献。另按 eval 模式融合视觉骨干的 34 对 Conv-BN。不改变图像分辨率，不删除有效 LiDAR 通道，不以未知道路或消失目标作为安全证据。

同权重 128 条有独立标签的开发输入，动作、风险和车道 argmax 全部一致，准确率分别保持 70.3125%、55.46875%、93.75%。浮点输出最大绝对差为 0.0006294，逐输出相对/绝对容差校验通过；这是代数等价改写的浮点容差一致，不是逐位相同。其余 96 条无标签输入不参与准确率统计。

| PyTorch 已注册算子的计数运算量 | 6,605,492,736 | 3,577,205,248 |

计数运算量降低约 45.845%，CPU P95 降低约 37.85%。两种运行顺序按样本交替，CPU20、单线程、低优先级，与原生场景运行并行。计数器只覆盖已注册算子，不是完整 SDK 算量审计；子图不包含递归事件头、语言编码、检测器和规则控制，不能直接作为整系统 FLOPs 比例。CPU 组件加速不换算成整链路/J6P 加速。

验证脚本和逐条指纹保存在 `exact_phase_fusion_v103/validation.json` 与 `evaluate_exact_fusion_v103.py`。该候选仍为影子实验，正在运行的完整三场景链路和默认权重未改变。

# Multi-Step Control Plan Execution

This module advances a structured multi-step DrivingIntent across CARLA frames
while keeping every transition in JSON. It does not infer completion merely
because an object disappears from perception. The controller or evaluator must
provide an explicit `StepFeedback` event.

## Files

- `control_plan_state.json`: persisted state of every intent step;
- `step_feedback.json`: explicit outcome for the currently active step;
- `control_decision.json`: the one flat action sent to the CARLA controller.

The stable contracts are:

- `scene_understanding/schemas/control_plan_state.schema.json`;
- `scene_understanding/schemas/step_feedback.schema.json`;
- `scene_understanding/schemas/control_decision.schema.json`.

## Initialize a plan

Do not pass `--state` or `--feedback` on the first frame:

```bash
python -m scene_understanding.scripts.advance_control_plan \
  --driving-intent inputs/driving_intent.json \
  --world-state inputs/world_state.json \
  --semantic-alignment outputs/semantic_alignment.json \
  --risk-assessment outputs/risk_assessment.json \
  --state-output outputs/control_plan_state.json \
  --decision-output outputs/control_decision.json
```

The initial active step is `intent.steps[0]`. A blocked step follows its
`on_blocked` policy:

- `WAIT_FOR_SAFE`: keep the step in `WAITING` and emit the safe fallback;
- `SKIP_STEP`: mark it `SKIPPED` and evaluate the next step;
- `SAFE_STOP` or an unknown policy: terminate the plan as `BLOCKED` and stop.

## Continue without completing the step

On a new WorldState frame, pass the prior state and omit feedback. The command
re-evaluates the same active step against the new alignment and risk files. It
can therefore recover automatically from `WAITING` when conditions become
safe, but it cannot advance to another step.

```bash
python -m scene_understanding.scripts.advance_control_plan \
  --driving-intent inputs/driving_intent.json \
  --world-state inputs/world_state_next.json \
  --semantic-alignment outputs/semantic_alignment_next.json \
  --risk-assessment outputs/risk_assessment_next.json \
  --state outputs/control_plan_state.json \
  --state-output outputs/control_plan_state.json \
  --decision-output outputs/control_decision.json
```

State replacement is atomic, so `--state` and `--state-output` may be the same
path.

## Complete and advance a step

The feedback must match the plan `request_id` and current `active_step_id`.
For example, `scene_understanding/schemas/examples/step_feedback.example.json` completes `step_1`:

```bash
python -m scene_understanding.scripts.advance_control_plan \
  --driving-intent inputs/driving_intent.json \
  --world-state inputs/world_state_next.json \
  --semantic-alignment outputs/semantic_alignment_next.json \
  --risk-assessment outputs/risk_assessment_next.json \
  --state outputs/control_plan_state.json \
  --feedback inputs/step_feedback.json \
  --state-output outputs/control_plan_state.json \
  --decision-output outputs/control_decision.json
```

`COMPLETED` activates the next step after checking `depends_on`. `FAILED` and
`CANCELLED` terminate the plan and emit `stop`. When all steps are completed,
the plan becomes `COMPLETED` and emits `keep_lane` at the current ego speed.

## Responsibility boundary

The executor owns ordering, persisted status, dependencies, and safety-gated
action selection. It does not decide that a maneuver physically completed.
During early JSON tests, feedback may be produced manually. In closed-loop
CARLA experiments it must be generated by the controller/evaluation layer from
measurable criteria such as target speed reached, lane ID changed, or route
goal reached.
